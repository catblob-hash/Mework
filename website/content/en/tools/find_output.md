`find_output` searches the output of one shell command this conversation has run and returns only the parts that match a plain-language `query`, without the model reading the transcript. The model reaches for it when a build, a test run or a server log is too long to take in whole — a background command still running, one a timeout moved to the task page, a finished command whose result has scrolled out of view — and it knows what it is after: the first error, whether the migration ran, which test hung. The command is named by the `shell:<id>` address `task_list` prints; a bare id is read the same way.

## Approval

It reads the host's own copy of the command's output and starts nothing — no file, no process, no page — so it classifies as a low-risk read (`host.read_or_coordinate`) and no security level asks about it, Plan mode included. Sending the blocks to TypeSafe is not a separate approval: enabling the tool and saving the key is the opt-in.

## Behavior and limits

Only this conversation's commands resolve: an address from another conversation reads exactly like one that never existed, and a `terminal:`, `workflow:` or `preview:` address is refused as not a shell task. Every command a shell tool ran counts — foreground or background, running or finished, in any shell, scored-output forms included. What is scored is what the task page keeps: the last 256 KiB, with standard output and standard error interleaved in the order they arrived rather than grouped as a tool result groups them. When the front has been dropped, the answer says how many bytes are gone, and line numbers count from the first line still kept. A running command is read as far as it has got; nothing waits for it. Finished commands stay readable across restarts until the conversation holds more than 400 of them or more than 32 MiB of their output, when the oldest go; one that was still running when Mework quit reads as finished without an exit code.

The answer opens with a status line the host writes itself — `shell:3 (bash) is still running`, `shell:3 (bash) was stopped`, `shell:3 (bash) finished with exit code 1` — which is never scored and never sent. A command that has printed nothing answers `shell:3 has produced no output to score.` without a request, so that answer needs no key. `query` is trimmed and capped at 2,000 characters; `threshold` must lie between 0 and 1 and is rounded to three decimals.

The text is cut into log records, the blocks this tool scores and returns: a line together with the lines that continue it — more deeply indented ones such as a stack trace, a `Caused by:`, and the exception line that ends a Python traceback. A command's output keeps no trace of how it was written — the retained output is one byte stream, and a program writing into a pipe usually flushes in 4 KiB blocks anyway — so the records are read off the text. Blank lines are not scored. Every block is scored on its own, with a question of its own, and several share one request: as many as the request budget holds — 1,500 characters for short material, then whatever keeps the call near 150 requests, up to 12,000 — and never more than 32. Requests run eight at a time, and every TypeSafe request Mework makes shares one pace — 32 at once after a quiet spell, then 18 a second, under TypeSafe's 1,200 a minute — so long material takes longer rather than coming back partly unscored. A block longer than 12,000 characters is scored in parts — along its lines, and a longer line in slices — and scores what its best part scores; it still comes back whole, its header naming the lines of the best part.

After the status line comes a count — `1 hit at or above 0.600 for query "…" (212 records of shell:3 output scored, 7 requests).` — then every record that cleared, highest score first, as `--- shell:3 output lines 212-214 (score 1.000) ---` followed by the whole record, each line with its number in the output, `cat -n` style. Scores carry the threshold's three decimals, so a reported score can be passed back as a threshold. When nothing clears, the answer says so and names the three best records with their scores. Output over 64 KiB is truncated.

Answers of `429` and `529` are retried twice, after 1 s and 2 s or the server's `Retry-After` up to 10 s, and each attempt has 30 s. A request that still fails leaves its blocks unscored, and the answer counts the failed requests and the blocks they left unscored; the call fails only when nothing at all was scored. A missing key, or one TypeSafe rejects, fails the call with a message pointing to the key setting. Stopping the run returns at once with `nothing was returned`; requests already in flight finish on their own.

## The decision model

`find_output` is its own row in the tool picker's **Shell** group, marked **Decision model**, beside the `shell` row rather than in its window; the **+** on the group heading switches it on with the shells. Seeded presets leave it off, because it cannot run until TypeSafe's key is saved under Global settings → Decision model providers. Each request sends TypeSafe's API the query and, for each of its records, the record's label — `shell:<id> output` and its line range — and its text; the status line and the command itself stay on the machine. A score is Jev's probability-weighted answer on four levels — unrelated, loosely related, relevant (contains part of what was asked), direct hit — mapped onto 0 to 1, so the levels sit at 0, 0.333, 0.667 and 1.
