# Mework built-in context injection: three-layer architecture

Built-in context injection is organized into three layers. This directory holds the generated snapshots of that surface; production behavior comes from `src-tauri/src/builtin_schemas.rs`, `src-tauri/src/catalog.rs`, `src-tauri/src/api.rs`, and dedicated renderers, and the JSON here is generated by code and pinned by tests.

## Three-layer model

1. **Fact layer (tool results / host notices):** These state what happened and nothing more. Dispatch receipts do not teach `next: …` usage; empty `task_list` results do not explain task creation; `ask_user` receipts are limited to "Asked the user; this turn is paused." An undrained subagent fold contains only its result envelope and is carried by host-generated `box` tool context rather than a User injection masquerading as a user message.
2. **Description layer (JSON Schema):** Schemas define what an item is, accurately and with its boundaries. Parameter limits are JSON Schema keywords (`minimum`/`maximum`, `minLength`/`maxLength`, `minItems`/`maxItems`, `enum`, `pattern`, `default`) and cross-field rules are `oneOf`/`not`/`dependentRequired`. Every schema root carries a factual description of the operation, including asynchrony, return value, and lifecycle. Numeric limits match host validation in `tool_executor.rs`, `browser.rs`, `orchestration.rs`, `mework_memory.rs`, `agents.rs`, and `workflow-core`, not UI copy. Keywords and parameter descriptions are always English. The **root** description is the exception: it is a prompt-profile key (`tool.<name>.description`), so it follows the selected profile — English by default, Chinese under the built-in Chinese profile, and whatever a handwritten file's `schemaNotes` says for that tool.
3. **Usage-guidance layer (tool description, `function.description`):** Seeds are entirely empty, and the three provider adapters omit the field when the description is empty. Users can set a tool description only through handwritten `.mework/tool-descriptions/*.json` files (prompt profiles) outside the application: `usageGuidance` fills this layer, while `schemaNotes` belongs to layer 2 and replaces that tool's root description outright — the two land on separate carriers rather than being concatenated. Both are visible to the model. The same file's `prompts` object overrides the fact-layer wording and every other host injection point (see the prompt-profile baselines below).

## Design files

- `builtin-tool-schemas.json`: Model-visible schema baseline. `tools` holds every public tool (with `toolCount`), `internalTools` holds the child-only `subagent_update` tool. Rust golden tests generate and pin it: `cargo test --lib -- builtin_schemas::tests::regenerate_builtin_schema_baseline --ignored` regenerates it, while the ordinary `builtin_schema_baseline_is_current` test prevents staleness. `structured_output` receives its schema from the caller and is not part of this baseline; the host adds one sentence of runtime semantics only when the caller's schema lacks a root description. The baseline forms of `agent_spawn` and `workflow` are **static**, not literal request payloads: top-level execution recreates them for named Agents available to the current conversation. `api.rs::inject_agent_type_schemas` writes the descriptor's `input_schema`, the first level of `tool_schema`'s fallback chain. When roles exist, `agent_spawn.agent_type` receives a name `enum` and `workflow` receives root-level `$defs.agentType`; with no roles, the `agent_type` property and its referencing `not` guard disappear together. Role names are therefore machine-readable schema constraints.
- `builtin-tool-catalog.zh-CN.json`, `builtin-tool-catalog.en-US.json`: Catalog snapshots for UI labels, parameter labels/help/placeholders, defaults, risk levels, and categories. `description` is always empty. UI fields are not included in model requests; the model-visible shape is in the schema baseline.
- `builtin-tool-descriptions.redesign.zh-CN.json`, `.en-US.json`: Authoring scaffolds for the usage-guidance layer — one `{ toolName, schemaNotes, usageGuidance }` entry per tool, all empty like the seeds. Users handwrite these files outside the app, copy them to a workspace or user-level `.mework/tool-descriptions/` directory, and select them explicitly in a session preset. The application offers no create, edit, or delete controls for them.
- `prompt-profile.en-US.json`, `prompt-profile.zh-CN.json`, `prompt-profile-keys.json`: The **prompt profile** baselines. Every host-authored, model-visible fixed text — MCP/hook sections, safety boundaries, the preview verification section (`system.preview_tools`), the subagent addendum, task receipts, the `box` delivery container's texts (`tool.box.description`, `task.box_no_op`), memory/skill/web-executor wording, file/shell tool framing — is one key in `src-tauri/src/prompt_profile.rs`. The conversation's own system prompt is not among them: it is a per-conversation setting the user types in the UI, and a blank one contributes nothing. The English file is `src-tauri/prompt-profiles/en-US.json` re-serialized through the same struct; the Chinese file is `src-tauri/prompt-profiles/zh-CN.json` re-serialized the same way; the keys file lists every key with its placeholders and where it is injected. Four keys ship an *empty* default — the web-evidence texts `system.web_safety`, `web.findings_notice`, `web.results_notice`, and `web.untrusted_marker` — and a profile that fills them in restores the wording with no code change. Both profiles are compiled in and always selectable; a handwritten `.mework/tool-descriptions/*.json` file uses the same shape (`name`, `prompts`, `tools`) and overrides any subset, falling back to the built-in for the application language. The ignored `prompt_profile::tests::regenerate_prompt_profile_baselines` test regenerates them and `prompt_profile_baselines_are_current` pins them. The documentation site (`website/`) renders its key reference from these files. Tool error messages and structural tokens (`[Image #N]`, envelope brackets, `<task-notification>`) are not keys.
- `scripts/export-context-injections.mjs`: Regenerates catalog snapshots and redesign scaffolds from `catalog.rs`; `--check` verifies them only. It does not manage the schema baseline, which Rust golden tests export from `json!` macros.

## Visible-tool boundary

The public catalog holds the file and command tools (`ls`, `grep`, `powershell`, `bash`, `write`, `edit`, `find`, `read`, `lsp`), the two web tools (`web_search`, `web_fetch`), the 15 `preview_*` tools that drive the built-in preview page (`preview_start`, `preview_stop`, `preview_list`, `preview_logs`, `preview_console_logs`, `preview_screenshot`, `preview_snapshot`, `preview_inspect`, `preview_click`, `preview_fill`, `preview_eval`, `preview_network`, `preview_resize`, `preview_upload_image`, `preview_dialog`), the orchestration tools (`agent_spawn`, `send_message`, `followup_task`, `task_wait`, `task_list`, `box`, `skill`, `tool_search`, `workflow`, `todo`, `ask_user`, `fork`, `plan`, `exit_plan_mode`, with 4 `todo` actions and 2 `plan` actions), and the 6 long-term-memory tools (`read_global_memory`, `read_project_memory`, `create_global_memory`, `create_project_memory`, `edit_global_memory`, `edit_project_memory`). Host-generated internal tools — `subagent_update` and `structured_output` — and synthesized `workflow_step` tool context sit outside the catalog. Internal-tool description seeds are also empty; their semantics live in the schema root description.

Several catalog names are not independently user-switchable, because the host derives them and keeps them out of persisted enabled lists (`isHostDerivedToolName` in `src/lib/taskTools.ts`, whose name sets mirror their Rust counterparts): the 6 memory tools follow the memory-layer switches, `task_wait` / `task_list` / `box` appear whenever a task-producing tool is enabled, `web_search` / `web_fetch` follow the conversation's single web-access switch, `skill` follows its on-demand skill switch, `tool_search` follows the MCP tool-discovery switch, and `plan` / `exit_plan_mode` follow the conversation's security level. `plan_mode::derived_tools` reads that level together with the subagent depth: both tools in plan mode at the top level, neither outside it, and neither inside a child agent at any level. Entering plan mode is the user's own choice in the composer; there is no tool for it.

`tool_schema` in `src-tauri/src/aisdk/tools.rs` resolves a tool's schema in four steps: the descriptor's own `input_schema`, `builtin_schemas::builtin_tool_schema`, the legacy `memory_tool_schema` (`memory_list`, `memory_read`, `memory_search`, `memory_upsert`, `memory_delete` — names the catalog does not carry), then a generic schema built from the descriptor's parameters.

## Model-visible injection points

| ID | Behavior |
| --- | --- |
| `tool.public-catalog` | Description seeds are empty and an empty field is omitted from the request; the schema is the hand-written authority in `builtin_schemas.rs` (boundaries as keywords, semantics in the root description). |
| `tool.internal-child` | `subagent_update` has an empty description and a dedicated schema; `structured_output` has an empty description, and the host adds runtime semantics only when the caller's schema lacks a root description. |
| `tool.execution-results` | `agent_spawn` / `workflow` / `web_search` dispatch receipts state facts only, with no usage teaching (the `workflow` receipt keeps `run_id`, the recovery handle); empty `task_list` results are terse; an undrained fold is only its result envelope, carried by host-synthesized, signed `box` tool context. |
| `tool.ask-user-pending` | "Asked the user; this turn is paused." (byte-synchronized with `src/types.ts`). |

Live results and their public projection are separate. The provider continuation receives the full tool result; renderer events, hook payloads, receipts, and persisted timeline contexts receive `public_tool_input` / `public_tool_result` instead — a memory call is reduced to `{operation, tier, status, name, bytes}`, and a `workflow` call carries the script's fingerprint rather than its body.

## Safety layer

The safety layer sits outside the three-layer model: `system.web_safety` (appended by `aisdk::step::combined_system_prompt` whenever `web_search` is enabled), the subagent addendum, the web-executor system prompt (`web.executor_system_prompt` with one of the two budget lines), project-memory UNTRUSTED wrapping, and the Chat image bridge prefix. The preview tools do not add `system.web_safety`; the section they gate is `system.preview_tools`, on `preview_start` plus the workspace launch config's own `autoVerify`.

## Override semantics

A tool's model-visible description is the root `description` of its JSON Schema, and that string is a registry key (`tool.<name>.description`), not a literal in `builtin_schemas.rs`. The override path follows from that:

1. Non-empty `schemaNotes` for a tool overrides that key, so it **replaces** the built-in wording instead of arriving beside it. `PromptProfile::from_file` performs the fold, which is why an equivalent `prompts` entry works too; `schemaNotes` wins when a file sets both.
2. The two built-in profiles differ here. `prompt-profiles/en-US.json` holds the English wording of every tool's key and `prompt-profiles/zh-CN.json` translates it. Selecting the Chinese profile therefore changes what the model is told each tool is — the schema is no longer English-only, though its *keywords* and parameter descriptions still are.
3. Non-empty `usageGuidance` fills `ToolDescriptor.description` (`function.description`), on top of an empty seed. It never merges with `schemaNotes`: the two ride separate carriers.
4. MCP tools have no registry key — their description comes from the remote server. `api::attach_mcp_tools` applies the same rule to the descriptor itself: `schemaNotes` replaces the server's text and `usageGuidance` is appended below it.
5. A `toolName` that names neither a built-in tool nor an `mcp__…` tool reaches nothing. The catalog entry says so (`N 个工具描述（M 个工具名无法匹配，不会生效）`) rather than counting it as a working override.
6. Parameter schemas, permissions, risk levels, and execution paths are unaffected.

`skill` is the one built-in without a `tool.<name>.description` key: its description stays on `skill.tool_description`. `PromptKey::for_tool_description` maps the tool name onto it, so `schemaNotes` for `skill` behaves like every other tool.
