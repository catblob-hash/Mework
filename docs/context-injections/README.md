# Mework built-in context-injection baseline: three-layer architecture

Built-in context injection is organized into three layers. This directory is the authoritative design baseline. Production behavior is defined by `src-tauri/src/builtin_schemas.rs`, `src-tauri/src/catalog.rs`, `src-tauri/src/api.rs`, and dedicated renderers; the JSON here is generated by code and pinned by tests.

## Three-layer model

1. **Fact layer (tool results / host notices):** State only what happened and keep it as short as possible. Do not inject information unless the model must see it. Dispatch receipts do not teach `next: …` usage; empty `task_list` results do not explain task creation; `ask_user` receipts are limited to "Asked the user; this turn is paused." An undrained subagent fold contains only its result envelope and is carried by host-generated `task_wait` tool context rather than a User injection masquerading as a user message.
2. **Description layer (JSON Schema):** Schemas define what an item is, accurately and with its boundaries. Express parameter limits using JSON Schema keywords (`minimum`/`maximum`, `minLength`/`maxLength`, `minItems`/`maxItems`, `enum`, `pattern`, `default`) and cross-field rules using `oneOf`/`not`/`dependentRequired`. Every schema root includes a factual description of the operation, including asynchrony, return value, and lifecycle. Numeric limits match host validation in `tool_executor.rs`, `browser.rs`, `orchestration.rs`, `mework_memory.rs`, `agents.rs`, and `workflow-core`, not UI copy. Keywords and parameter descriptions are always English. The **root** description is the exception: it is a prompt-profile key (`tool.<name>.description`), so it follows the selected profile — English by default, Chinese under the built-in Chinese profile, and whatever a handwritten file's `schemaNotes` says for that tool.
3. **Usage-guidance layer (tool description, `function.description`):** Seeds are entirely empty. The three provider adapters omit the field when the description is empty. Users can set a tool description only through handwritten `.mework/tool-descriptions/*.json` files (prompt profiles) outside the application: `usageGuidance` fills this layer, while `schemaNotes` belongs to layer 2 and replaces that tool's root description outright — the two land on separate carriers rather than being concatenated, because "what this tool is" and "how to use it here" are different claims. Both are visible to the model. The same file's `prompts` object overrides the fact-layer wording and every other host injection point (see the prompt-profile baselines below).

## Design files

- `builtin-tool-schemas.json`: Model-visible schema baseline for the 27 public tools and the internal `subagent_update` tool. Rust golden tests generate and pin it: run `cargo test --lib -- builtin_schemas::tests::regenerate_builtin_schema_baseline --ignored` to regenerate it, while the ordinary `builtin_schema_baseline_is_current` test in `cargo test` prevents staleness. `structured_output` receives its schema from the caller and is not part of this baseline; the host adds one sentence of runtime semantics only when the caller's schema lacks a root description. The baseline forms of `agent_spawn` and `workflow` are **static**, not literal request payloads: top-level execution recreates them for named Agents available to the current conversation. `api.rs::inject_agent_type_schemas` writes the descriptor's `input_schema`, the first of four `tool_schema` discriminators. When roles exist, `agent_spawn.agent_type` receives a name `enum` and `workflow` receives root-level `$defs.agentType`; with no roles, the `agent_type` property and its referencing `not` guard disappear together. Role names are therefore **machine-readable schema constraints**, not a prose list that can drift from documentation.
- `builtin-tool-catalog.zh-CN.json`, `builtin-tool-catalog.en-US.json`: Catalog snapshots for UI labels, parameter labels/help/placeholders, defaults, risk levels, and categories. `description` is always empty. UI fields are not included in model requests; see the schema baseline for model-visible shape.
- `builtin-tool-descriptions.redesign.zh-CN.json`, `.en-US.json`: Authoring scaffolds for the usage-guidance layer, entirely empty like the seeds. Users must handwrite these files outside the app, copy them to a workspace or user-level `.mework/tool-descriptions/` directory, and explicitly select them in a session preset. The application does not offer create, edit, or delete controls.
- `prompt-profile.en-US.json`, `prompt-profile.zh-CN.json`, `prompt-profile-keys.json`: The **prompt profile** baselines. Every host-authored, model-visible fixed text — MCP/hook sections, safety boundaries, the subagent addendum, task receipts, notification preamble, memory/skill/web-executor wording, file/shell tool framing — is one key in `src-tauri/src/prompt_profile.rs`. The conversation's own system prompt is not among them: it is a per-conversation setting the user types in the UI, and a blank one contributes nothing. The English file is the hard-coded default rendered from that registry; the Chinese file is `src-tauri/prompt-profiles/zh-CN.json` re-serialized through the same struct; the keys file lists every key with its placeholders and where it is injected. A few keys ship an *empty* default — the four web-evidence texts (`system.web_safety`, `web.findings_notice`, `web.results_notice`, `web.untrusted_marker`), because a search backend the user configured is a trusted one; the keys remain so a profile can put the wording back. Both profiles are compiled in and always selectable; a hand-written `.mework/tool-descriptions/*.json` file uses the same shape (`name`, `prompts`, `tools`) and overrides any subset, taking the application language as the built-in it falls back to. Regenerate with `cargo test --lib -- prompt_profile::tests::regenerate_prompt_profile_baselines --ignored`; `prompt_profile_baselines_are_current` pins them. The documentation site (`website/`) renders its key reference from these files. Tool error messages and structural tokens (`[Image #N]`, envelope brackets, `<task-notification>`) are deliberately not keys.
- `scripts/export-context-injections.mjs`: Regenerates catalog snapshots and redesign scaffolds from `catalog.rs`; `--check` verifies them only. It does not manage the schema baseline, which Rust golden tests export from `json!` macros.

## Visible-tool boundary

The public catalog has 27 tools: 8 file and command tools; 3 web tools (`web_search`, `web_fetch`, `playwright`, the last with 23 actions); 10 agent-orchestration tools (`agent_spawn`, `send_message`, `followup_task`, `task_wait`, `task_list`, `skill`, `workflow`, `todo`, `ask_user`, `fork`, with 4 `todo` actions); and 6 long-term-memory tools. Host-generated internal tools, `subagent_update` and `structured_output`, plus synthesized `workflow_step` tool context, remain unchanged. Internal-tool description seeds are also empty; semantics are in the schema root description.

Eight of the 27 tools are not independently user-switchable: the 6 memory tools derive from the memory layer, while `task_wait` and `task_list` derive whenever any task-producing tool is enabled.

## Model-visible injection points

| ID | Behavior |
| --- | --- |
| `tool.public-catalog` | Description seeds are empty and an empty field is omitted from the request; the schema is the hand-written authority in `builtin_schemas.rs` (boundaries as keywords, semantics in the root description). |
| `tool.internal-child` | `subagent_update` has an empty description and a dedicated schema; `structured_output` has an empty description, and the host adds runtime semantics only when the caller's schema lacks a root description. |
| `tool.execution-results` | `agent_spawn` / `workflow` / `web_search` dispatch receipts state facts only, with no usage teaching (the `workflow` receipt keeps `run_id`, the recovery handle); empty `task_list` results are terse; an undrained fold is only its result envelope, carried by host-synthesized, signed `task_wait` tool context. |
| `tool.ask-user-pending` | "Asked the user; this turn is paused." (byte-synchronized with `src/types.ts`). |

The safety layer is outside the three-layer model and remains unchanged: `system.web-safety`, subagent V1 (frozen) / V2 addendum, the web-executor system prompt, project-memory UNTRUSTED wrapping, and the Chat image bridge prefix.

## Override semantics

A tool's model-visible description is the root `description` of its JSON Schema, and that string is a registry key (`tool.<name>.description`), not a literal in `builtin_schemas.rs`. Both consequences matter:

1. Non-empty `schemaNotes` for a tool overrides that key, so it **replaces** the built-in wording instead of arriving beside it. `PromptProfile::from_file` performs the fold, which is why an equivalent `prompts` entry works too; `schemaNotes` wins when a file sets both, because it is the channel the authoring scaffold is about.
2. The two built-in profiles differ here. The English defaults are the hard-coded registry values; `prompt-profiles/zh-CN.json` translates every tool's key. Selecting the Chinese profile therefore changes what the model is told each tool is — the schema is no longer English-only, though its *keywords* and parameter descriptions still are.
3. Non-empty `usageGuidance` fills `ToolDescriptor.description` (`function.description`), on top of an empty seed. It never merges with `schemaNotes`: the two ride separate carriers.
4. MCP tools have no registry key — their description came from the remote server. `api::attach_mcp_tools` applies the same rule to the descriptor itself: `schemaNotes` replaces the server's text and `usageGuidance` is appended below it.
5. A `toolName` that names neither a built-in tool nor an `mcp__…` tool reaches nothing. The catalog entry says so (`N 个工具描述（M 个工具名无法匹配，不会生效）`) rather than counting it as a working override.
6. Parameter schemas, permissions, risk levels, and execution paths are unaffected.

`skill` is the one built-in without a `tool.<name>.description` key: its description predates this section and stays on `skill.tool_description`. `PromptKey::for_tool_description` maps the tool name onto it, so `schemaNotes` for `skill` behaves like every other tool.

## Regeneration and verification

```powershell
node scripts/check-catalog-parity.mjs
node scripts/export-context-injections.mjs --check
cargo test --lib -- builtin_schemas::
```

When the schema baseline is stale:

```powershell
cargo test --lib -- builtin_schemas::tests::regenerate_builtin_schema_baseline --ignored
```

## Remaining boundaries

- `playwright` does not trigger `WEB_HOST_SAFETY_PROMPT`; only `web_search` does.
- Legacy `memory_*` schemas remain as a compatibility-only dead path through `api.rs::memory_tool_schema`; they are not among the 27 active tools.
- The separation between live results and persisted projection (`public_tool_input`/`public_tool_result`) is unchanged.
